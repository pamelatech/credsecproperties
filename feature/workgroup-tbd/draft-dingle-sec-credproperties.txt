1.  Introduction

   A credential is a set of data used to validate, confirm, or establish
   one or more claims about a named entity.  Many diverse types of
   credential may be used to identify, authenticate, or otherwise
   validate a subject, and yet there is no specific vocabulary that
   describes exactly what a given credential should be expected to do,
   or why exactly it can be called "secure".  To address this
   shortcoming, this document describes categories of secure credential
   management and defines _exact_ labels to describe the intended
   operation of a given credential.  These labels are intended for
   colloquial use and designed whenever possible to be accessible and
   intuitive for laypeople.  The specification is scoped only to a
   credential in its common and expected use; properties for secure
   administration of credentials are not part of this set.  Negative
   uses (attacks, vulnerabilities) are also not in scope.

2.  Credential Management Security Classes

   Properties are organized into areas of scrutiny, with each class
   containing the minimum set of properties possible to satisfy
   differences that have clear security value.  The property must have a
   security benefit that is inherent to the credential type.

3.  Credential Management Security

3.1.  Credential Construction Properties

3.1.1.  Substantiation

   Substantiation describes credentials containing mechanisms for
   authoritative statements that can be externally validated.  Examples
   of substantiated credentials include attestations such as SAML
   assertions [SAML] or X.509 certificates [RFC5280].

3.1.2.  Dynamism

   Dynamism describes a credential whose inactive (stored or at-rest)
   and active forms are different.  Credentials with no dynamism (or
   dynamic generativity) such as passwords exhibit no difference between
   the stored value (in memory, in a password manager, etc.) and the
   credential sent to the verifier.  Dynamic generativity indicates that
   some function is used to operate on the stored credential such that
   what is sent over the wire is different than what is stored (e.g. a
   challenge response protocol like FIDO [WEBAUTHN]).  Credentials that
   do not exhibit dynamism, such as shared secrets, usually exhibit
   replayability and are definitionally not able to be contained (see
   Section 3.3).

3.1.3.  Bindability

   Bindability describes whether a credential or its presentation can
   provide verifiable evidence of a relationship between the credential
   or its claims and one or more entities or contexts.  These
   relationships can involve an issuer, subject, audience, communication
   channel, or device, and can be established or evaluated during
   issuance or presentation.  When a credential is constructed to be
   bindable, a receiver of a credential can validate each present
   binding to mitigate potential threat vectors.

3.1.4.  Tamper Proofness

   A mechanism for credential integrity is built into the credential
   ensuring that the data within the credential is verifiably unchanged
   by external parties.

3.1.5.  Chainability

   The credential is capable of including links to or content of other
   credentials.

3.1.6.  Audience Restriction

   A mechanism that specifies which destination consumers of the
   credential are valid.  Examples include id_token values [OIDC-CORE]
   or origin bindings of FIDO tokens.  Consumers of the credential
   should be responsible for validating the audience restriction before
   using an audience-restricted credential.

3.1.7.  Validity Window

   A credential becomes invalid outside of a specified time boundary.
   An example would be a SAML assertion or a TOTP [RFC6238].

3.1.8.  Selective Disclosure

   A credential is capable of selective disclosure if some or all of the
   contents within a credential can be made available or unavailable
   under circumstances determined at presentation time.  Values can be:
   none, per-claim, or predicate.

   *  None: the credential is presented whole, or not at all.

   *  Per-claim: individual claims can be revealed or withheld at
      presentation time.  The mechanism may be a salted hash over each
      claim, as in an SD-JWT [RFC9901] or an ISO mdoc [ISO18013-5], or a
      zero-knowledge proof over the issuer's signature, as in a
      credential signed with the BBS signature scheme
      [I-D.irtf-cfrg-bbs-signatures].

   *  Predicate: a statement about a claim can be proven without
      revealing the claim itself, such as proving that an age exceeds a
      threshold rather than disclosing a date of birth.  Predicates
      require a proof construction beyond selective disclosure alone,
      such as a range proof; the BBS signature scheme selectively
      discloses claims but does not itself prove predicates.

   Selective disclosure describes what a presentation reveals.  Whether
   presentations can be correlated with each other is a separate
   property, Unlinkability (Section 3.2.3); a credential may selectively
   disclose and still be fully linkable.

3.2.  Credential Presentation

   Credential presentation properties describe ways in which the use of
   a credential is functionally restricted.

3.2.1.  Usage Count Limit

   A credential is usage count limited if it becomes invalid after a
   specified number of successful presentations by a legitimate
   presenter.  An example would be a temporary password that can only be
   used 5 times, or a one-time password.

3.2.2.  Replayability

   Credentials are replayable when they can be captured by an adversary
   and represented to an authentication service resulting in successful
   authentication.  Credentials that are presented directly, such as
   shared secrets (passwords) or bearer tokens, are the canonical
   example of replayable credentials.  Challenge response protocols are
   considered non-replayable.

   OTPs represent an interesting class of crentials when describing
   replayability.  Deployed at a global scale, there is a small window
   of opportunity to present a HOTP [RFC4226] or TOTP multiple times
   within its validity window.  Therefore, replayability is not a
   strictly binary scale.

3.2.3.  Unlinkability

   Unlinkability describes whether two presentations of a credential can
   be correlated with each other, or with the issuance of the
   credential, by the parties that observe them.  A presentation that
   carries a static value such as an issuer signature, a certificate
   serial number, or a public key is linkable by any party that sees
   that value twice.  [RFC9901] Section 10.1 distinguishes unlinkability
   between presentations, between verifiers, and between issuer and
   verifier, and observes that salted hash selective disclosure cannot
   achieve the last of these because the issuer-signed credential is
   presented directly to the verifier.  The following table defines
   possible values.

   +=====================+===========+================================+
   | Value               | Who Can   | Characteristics                |
   |                     | Correlate |                                |
   +=====================+===========+================================+
   | Linkable            | Any       | Presentations carry a static   |
   |                     | observer  | correlator.  Examples include  |
   |                     |           | X.509 certificates, bearer     |
   |                     |           | tokens, SD-JWTs, and ISO       |
   |                     |           | mdocs, each of which presents  |
   |                     |           | the issuer's signature         |
   |                     |           | verbatim.                      |
   +---------------------+-----------+--------------------------------+
   | Verifier-unlinkable | Issuer    | Verifiers cannot correlate     |
   |                     | together  | presentations with each other, |
   |                     | with a    | whether at one verifier or     |
   |                     | verifier  | across verifiers, but each     |
   |                     |           | presentation still carries a   |
   |                     |           | value the issuer saw at        |
   |                     |           | issuance, so an issuer that    |
   |                     |           | compares notes with a verifier |
   |                     |           | can link a presentation to its |
   |                     |           | issuance.  Batch issuance of   |
   |                     |           | single-use SD-JWTs with        |
   |                     |           | distinct salts and Key Binding |
   |                     |           | keys achieves this [RFC9901].  |
   +---------------------+-----------+--------------------------------+
   | Issuer-unlinkable   | No party  | Each presentation is a freshly |
   |                     |           | derived proof carrying no      |
   |                     |           | value that was visible at      |
   |                     |           | issuance, so even a colluding  |
   |                     |           | issuer and verifier cannot     |
   |                     |           | link a presentation to its     |
   |                     |           | issuance.  Examples include a  |
   |                     |           | credential signed with the BBS |
   |                     |           | signature scheme               |
   |                     |           | [I-D.irtf-cfrg-bbs-signatures] |
   |                     |           | and a Privacy Pass token       |
   |                     |           | [RFC9577].                     |
   +---------------------+-----------+--------------------------------+

                                 Table 1

   An issuer-unlinkable credential may be deliberately linkable within a
   single verifier when the holder derives a pseudonym that is stable
   for one verifier and unlinkable across verifiers
   [I-D.irtf-cfrg-bbs-per-verifier-linkability].  The values above
   describe the credential mechanism only; disclosed claim values,
   identifiers, and transport metadata can correlate presentations
   regardless of the mechanism, as described in Section 8 of
   [VC-DATA-MODEL].

   Unlinkability is independent of Referential Identity Posture.
   Posture describes whose identity is asserted; unlinkability describes
   whether presentations can be correlated.  A credential with a Direct
   posture can be issuer-unlinkable, and a credential with a
   Pseudonymous posture is linkable whenever the same pseudonym is
   presented each time.

3.2.4.  Referential Identity Posture

   Referential Identity Posture describes the nature of the relationship
   between a claimed identity validated as part of an identity
   transaction and any backing identity that might explicitly or
   implicitly exist in a larger security context.  That larger context
   may or may not be known to the party validating the credential and
   represents environmental detail that could be used in security, risk,
   or governance activities if known.  The following table defines
   possible postures.

      +==============+============+================================+
      | Posture      | Backing    | Relationship Characteristics   |
      |              | Identity   |                                |
      |              | Visibility |                                |
      +==============+============+================================+
      | Direct       | Explicit   | Claimed identity and backing   |
      |              |            | identity are the same entity.  |
      +--------------+------------+--------------------------------+
      | Delegated    | Explicit   | Claimed identity is distinct   |
      |              |            | from the backing identity, and |
      |              |            | the relationship is explicitly |
      |              |            | communicated.                  |
      +--------------+------------+--------------------------------+
      | Impersonated | Implicit   | Claimed identity is presented  |
      |              |            | as the backing identity; the   |
      |              |            | underlying relationship exists |
      |              |            | but is external, inferred, or  |
      |              |            | hidden.                        |
      +--------------+------------+--------------------------------+
      | Partitioned  | Partial    | Claimed identity represents a  |
      |              |            | constrained portion or view of |
      |              |            | a backing identity; the        |
      |              |            | linkage is incomplete or only  |
      |              |            | partially disclosed.           |
      +--------------+------------+--------------------------------+
      | Pseudonymous | Obfuscated | A backing identity exists, but |
      |              |            | the relationship between the   |
      |              |            | claimed identity and backing   |
      |              |            | identity is intentionally      |
      |              |            | concealed or only recoverable  |
      |              |            | by an authorized authority.    |
      +--------------+------------+--------------------------------+
      | Chained      | Recursive  | Claimed identity derives from  |
      |              |            | a backing identity through one |
      |              |            | or more intermediate           |
      |              |            | referential identities,        |
      |              |            | forming a transitive chain of  |
      |              |            | relationships.                 |
      +--------------+------------+--------------------------------+
      | Anonymous    | Detached   | Claimed identity is visibly    |
      |              |            | severed from any backing       |
      |              |            | identity with no opportunity   |
      |              |            | to recover.                    |
      +--------------+------------+--------------------------------+

                                 Table 2

   Examples of delegated referential identity posture include on-behalf-
   of (OBO) token interactions [RFC8693], where both the identity of the
   end user and client software are communicated.  Token exchange draws
   the same distinction normatively: a delegated actor retains its own
   identity while acting as an agent for another party, whereas an
   impersonating actor gains the rights of the party it impersonates and
   is indistinguishable from it.  Examples of impersonated referential
   identity posture might include privileged access management
   workflows, where an administrative process sets either the identifier
   or the credential (or both) based on a backing identity.  Examples of
   a partitioned referential identity posture could include openclaw
   agents acting with separate accounts and email addresses but loosely
   affiliated to individuals.  Examples of a chained referential
   identity posture include transaction tokens
   [I-D.ietf-oauth-transaction-tokens], which preserve the identity of
   the original caller as a request traverses a call chain of workloads,
   and which require the chain of workloads that requested a token to be
   carried forward each time that token is replaced.  Token exchange
   expresses the same structure directly through nested actor claims,
   where the outermost actor is the current party and each nested actor
   a prior one.  Examples of a pseudonymous referential identity posture
   include a credential presented under a per-verifier pseudonym
   [I-D.irtf-cfrg-bbs-per-verifier-linkability], where the issuer holds
   a backing identity that the pseudonym conceals from the verifier.
   Examples of an anonymous referential identity posture include a
   Privacy Pass token [RFC9577], which proves that an issuer vouched for
   the holder without identifying the holder, and a BBS proof that
   discloses only non-identifying claims, where the issuer attests a
   fact about the holder that no party can trace back to an individual.

3.3.  Credential Containment & Unlock

   Credential containment describes the at-rest state of a credential
   and its storage location(s).  Unlock properties describe how the
   contained credential is made available for use at runtime and how the
   containment facility, if any, can play a security role in an
   observable way at operation time.

3.3.1.  Containment

   Describes how the creation, storage, and usage of a credential is
   managed.  At one extreme, containment be within the boundary of a
   cryptographically supervised service or hardware element, e.g. an SSH
   private key [RFC4251] stored in an HSM.  At the other extreme, the
   credential may be uncontained, e.g. a manually generated password.  A
   SSH private key stored on volatile media sits between these extremes,
   it is contained by access to the media on which it resides but it is
   not permanently bound to the media (see Boundary Binding, below).

3.3.2.  Boundary Binding

   Boundary bindings describe the operational rules or limitations that
   limit where the secret portion of a credential could be stored.  In
   the prior examples, the HSM bound SSH private key may not be
   extractable from the HSM, the HSM provides the boundary binding.  The
   password is unbounded, there are no limits on how the password may be
   moved or shared.  The SSH key stored on volatile media is also
   unbound, since it may be copied and moved freely, e.g. it is
   exportable.

3.3.3.  Boundary Enforcement

   The boundary enforcement property describes the mechanisms which
   ensure that operational rules are followed.  Boundary enforcements
   can be proactive or reactive.  An example of a proactive boundary
   enforcement include binding the credential to the device, e.g. the
   SSH key generated and stored in an HSM.  An example of a reactive
   boundary enforcement includes credential scanning of source code
   repositories.

3.3.4.  Transference

   Transference is the ability for an end user to give the credential
   away to another user such that durable ongoing use is possible by two
   different entities.  This transference may be within the enforced
   boundary (e.g. sharing a synced passkey via a credential manager) or
   outside of the boundary (e.g. user copies a password from a
   credential manager to a file which is emailed to another user).

3.3.5.  Activation

   A credential becomes available for an operation only when a local
   user gesture is performed.  This user gesture may also be called an
   activation factor [SP800-63B-rev4].  Only a credential that is
   contained can be activated.  A FIDO2 private key on a hardware
   security device that requires a PIN is an example of an activated
   credential.  A biometric that unlocks a TPM on a laptop is another
   example of an activated credential.  Presence Activation is a case
   where locality is required but confirmation of a secret or biometric
   is not required.  Individual Activation is a case where only one
   human can trigger the container to unlock.

3.3.6.  Unlock Scope

   A credential may be unlocked by different parties which defines the
   scope of which entities can unlock credential for use.  The owner of
   a credential is always expected to be able to unlock their own
   credential.  Credentials on shared devices may be unlocked by all
   users sharing the device.  Similarly, credentials in a shared
   enterprise vault may be unlocked by a vault administrator.  Unlock
   scope is related to an instance of a credential and is distinct from
   the Credential Management Security Properties.

3.3.7.  Unlock Persistence

   Credentials may be unlocked once with an activation factor (e.g.
   entering a PIN or biometric to activate a hardware security key), or
   the activation factor may be presented seconds to minutes before use
   (e.g. a credential vault remains unlocked for 5 minutes after use,
   allowing presentation of credentials from the vault without further
   activation).

3.4.  Credential Enrollment

   Credential enrollment properties describe requirements required to be
   met before a credential is created.

3.4.1.  Enrollment Assurance

   Enrollment assurance describes the identity verification assurance
   level, such as the identity assurance levels defined in
   [SP800-63A-rev4], at the time the credential was created.

3.4.2.  Vouching

   A vouched credential is one whose enrollment was enabled by the
   subject first authenticating with a separate, pre-existing
   credential.  The prior credential acts as a gate on the enrollment
   event but does not contribute its key material to the new credential.
   After enrollment, the vouched credential is fully independent.  A
   user may present a passport as a proof of citizenship to be granted a
   state digital identity.

3.4.3.  Enrollment Binding

   Enrollment binding describes the mechanism that binds the credential
   to the enrolled identity.

3.5.  Credential Compliance

   Credential provider compliance properties describe requirements on
   composition or management dictated by regulatory bodies.

3.5.1.  Composition Rules

   Composition rules describe regulatory or standards-based requirements
   on how the credential must be constructed such as acceptable
   cryptographic algorithms.

3.5.2.  Lifecycle Rules

   Lifecycle rules describe regulatory or standards-based requirements
   on credential rotation, expiry, or revocation.

3.5.3.  Regulatory Framework

   Regulatory framework describes which regulatory framework or
   frameworks impose requirements on this credential type.  Multiple
   values may apply simultaneously.

3.6.  Credential Recovery

   Credential Recovery properties describe limitations of who can reset
   a credential or how a credential can be reset.

3.6.1.  Recoverability

   Recoverability describes remediation capabilities that enable or re-
   enable access to a valid credential after loss or compromise.  Values
   can be: issuer-driven, container-driven,or account-driven. * Issuer-
   driven: remediation is enabled by a direct party to the creation of
   the credential.  Examples include credentials with multiple
   configured signing certificates, synced passkeys protected by a
   consumer trust layer, or hardware keys created with matching/derived
   seed values. * Container-driven: remediation enabled by a direct
   party to containment or unlock of the credential with pre-established
   administrative trust.  Examples include PAM (privileged access
   management) systems or corporate password managers. * Account-driven:
   the credential cannot be restored, it can only be removed and
   replaced, often through a process that requires presentation of an
   unrelated alternate credential.

4.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   *Credential:* Information or a mechanism used by a subject to prove a
   claim to a verifier.  Depending on the credential type, it may
   include a stored secret or key, a value generated from that secret or
   key for presentation, or an assertion issued by another party.  The
   stored and presented forms may be identical or different, as
   described by Section 3.1.2.

Appendix A.  Applying the Properties to Common Credential Types

   This appendix illustrates how the properties defined in this document
   apply to a range of common credential types, to validate that the
   property set is expressive enough to differentiate them.  Each class
   of properties defined in Section 3 is presented as a table whose rows
   are credential types and whose columns are the properties of that
   class.

   The credential types examined are:

   *  *Password / API key / client credential* — a shared secret
      presented directly to the verifier with no transformation.

   *  *Synced passkey (consumer)* — a WebAuthn credential synchronized
      across devices by a consumer credential manager such as a platform
      provider or password manager.

   *  *Device-bound passkey on FIDO L2 Certified security key* — a
      WebAuthn credential generated on and bound to a hardware
      authenticator implementing CTAP [CTAP] and certified at FIDO L2 or
      above.

   *  *SPIFFE X.509-SVID* — a workload identity issued as an X.509
      certificate following attestation of the workload, presented via
      mutual TLS.  See [SPIFFE-X509-SVID].

   *  *SPIFFE JWT-SVID* — the same workload identity expressed as a
      signed JWT [RFC7519] and presented as a bearer token [RFC6750] to
      services that cannot terminate mutual TLS.  See [SPIFFE-JWT-SVID].

   *  *mTLS certificate* — a client certificate issued by a Web PKI or
      private CA outside of any SPIFFE trust domain, presented during
      the TLS handshake.

   *  *OAuth access token* — an access token [RFC6749] presented to a
      resource server, either as a signed JWT (bearer token) or as an
      opaque handle (reference token) the resource server validates by
      introspection.

   *  *Sender-constrained access token* — the same access token bound to
      a client key, so that presentation additionally requires proof of
      possession of that key, whether by DPoP [RFC9449] or by mutual TLS
      certificate binding [RFC8705].  By adding proof of possession, the
      token no longer displays the properties of bearer tokens, it is
      bound to the key holder.

   *  *ID-JAG* — an Identity Assertion JWT Authorization Grant
      [I-D.ietf-oauth-identity-assertion-authz-grant], a JWT issued by
      an enterprise identity provider when a client exchanges its ID
      token or SAML assertion for one, and presented by that client to a
      resource application's authorization server as a JWT authorization
      grant [RFC7523] to obtain an access token.

   *  *HOTP* — an HMAC-based counter-derived one-time password.

   *  *TOTP* — a time-derived one-time password.

   *  *SMS OTP* — a one-time code generated by the verifier and
      delivered out of band over the public telephone network.

   *  *SD-JWT VC* — a verifiable credential expressed as a selectively
      disclosable JWT [I-D.ietf-oauth-sd-jwt-vc], built on the SD-JWT
      construction, optionally bound to a holder key.

   *  *ISO mdoc* — an ISO/IEC 18013-5 mobile document such as a mobile
      driving licence, comprising an issuer-signed Mobile Security
      Object and a device-signed response.

   *  *BBS verifiable credential* — a verifiable credential
      [VC-DATA-MODEL] secured with the BBS signature scheme
      [I-D.irtf-cfrg-bbs-signatures] through the Data Integrity BBS
      cryptosuite [VC-DI-BBS], so that each presentation is a freshly
      derived zero-knowledge proof over the selectively disclosed claims
      rather than the issuer's signature itself.

   *  *DBSC* — Device Bound Session Credentials [DBSC], a browser
      session credential bound to a non-exportable device key and
      periodically refreshed by proof of possession.

A.6.  Credential Recovery

   +====================+==============================================+
   | Credential Type    | Recoverability                               |
   +====================+==============================================+
   | Password / API key | Account-driven; reset via an alternate       |
   |                    | credential, the prior secret is not          |
   |                    | restored                                     |
   +--------------------+----------------------------------------------+
   | Synced passkey     | Issuer-driven; the provider's account        |
   |                    | recovery restores the synced credential      |
   +--------------------+----------------------------------------------+
   | Device-bound       | Account-driven; a lost authenticator         |
   | passkey            | cannot be restored, a replacement must       |
   |                    | be enrolled against a backup credential      |
   +--------------------+----------------------------------------------+
   | SPIFFE X.509-SVID  | Issuer-driven; re-attestation yields a       |
   |                    | new SVID, recovery of the prior key is       |
   |                    | neither needed nor possible                  |
   +--------------------+----------------------------------------------+
   | SPIFFE JWT-SVID    | Issuer-driven; re-attestation yields a       |
   |                    | new SVID                                     |
   +--------------------+----------------------------------------------+
   | mTLS certificate   | Issuer-driven where the CA supports key      |
   |                    | escrow or re-issuance; Account-driven        |
   |                    | otherwise, by revoking and re-enrolling      |
   +--------------------+----------------------------------------------+
   | OAuth bearer       | Issuer-driven; a new token is requested      |
   | access token       | with a refresh token or a fresh              |
   |                    | authorization grant.  The token itself       |
   |                    | is never recovered                           |
   +--------------------+----------------------------------------------+
   | Sender-constrained | Issuer-driven; a new token is requested      |
   | access token       | and bound to a current key.  Loss of         |
   |                    | the bound key requires a new key and a       |
   |                    | new token                                    |
   +--------------------+----------------------------------------------+
   | ID-JAG             | Issuer-driven; a new grant is requested      |
   |                    | from the identity provider by token          |
   |                    | exchange.  The grant itself is never         |
   |                    | recovered                                    |
   +--------------------+----------------------------------------------+
   | HOTP               | Container-driven where an authenticator      |
   |                    | application backup restores the seed;        |
   |                    | Account-driven otherwise, by enrolling       |
   |                    | a new seed                                   |
   +--------------------+----------------------------------------------+
   | TOTP               | Container-driven where an authenticator      |
   |                    | application backup restores the seed;        |
   |                    | Account-driven otherwise, by enrolling       |
   |                    | a new seed                                   |
   +--------------------+----------------------------------------------+
   | SMS OTP            | Account-driven; recovery consists of         |
   |                    | regaining control of the phone number,       |
   |                    | typically through the carrier                |
   +--------------------+----------------------------------------------+
   | SD-JWT VC          | Issuer-driven; the holder re-requests        |
   |                    | issuance.  A wallet backup may restore       |
   |                    | the credential but not a hardware-bound      |
   |                    | Key Binding key                              |
   +--------------------+----------------------------------------------+
   | ISO mdoc           | Issuer-driven; reissuance by the             |
   |                    | issuing authority, the DeviceKey cannot      |
   |                    | be recovered                                 |
   +--------------------+----------------------------------------------+
   | BBS verifiable     | Issuer-driven; the holder re-requests        |
   | credential         | issuance.  A wallet backup may restore       |
   |                    | the credential and, where held in            |
   |                    | software, the holder secret                  |
   +--------------------+----------------------------------------------+
   | DBSC               | Account-driven; the session is re-           |
   |                    | established by re-authenticating and         |
   |                    | the device key is regenerated                |
   +--------------------+----------------------------------------------+
